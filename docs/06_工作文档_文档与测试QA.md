## 二、回归基线（v2.1 新增，最重要的一件事）

**问题**：老系统 0 用例、0 快照。W4 的"老功能回归通过"只能靠人点，而迁移类项目最典型的缺陷——金额少 1 分、日期差 8 小时、分页 total 差 1——**人点一遍一个都发现不了**。

**做法（1.5 人日）**：

```
1) 老系统跑起来，对 103 个 接口各录一份 { request, response } 存 tests/snapshots/
2) 写 30 条核心链路冒烟（登录→搜房→约看→申请→签约→报修→账单→评价）用 Newman
3) 新栈跑同样请求 → diff 快照
   白名单：traceId、时间戳、毫秒级浮点
   其余任何差异 → 视为回归缺陷
4) W2 起每天跑一次，红了当天查
```

**这条做完，W4 的"老功能不丢"才有证据；不做，P1 出口是主观判断。**

## 三、数据迁移对账（v2.1 新增）

| 类 | 校验 SQL / 方法 | 通过标准 |
|---|---|---|
| 金额 | 老库 `SUM(money)` vs 新库 `SUM(money_fen)/100`；抽样 100 行 `ABS(ROUND(money*100)-money_fen)` | 相等；抽样误差 0 |
| 密码 | 5 个老账号用原密码登录 | 全部成功，且 DB 内已是 bcrypt + `pwd_algo='bcrypt'` |
| 日期 | `COUNT(*) WHERE end_time IS NOT NULL AND end_date IS NULL` | 0（转换失败的行必须人工清单跟进，不允许静默） |
| 角色 | 每个老角色用户在新 `user_role` 有对应记录 | 100% 覆盖 |
| 租约状态 | `COUNT(*) WHERE status IS NULL` | 0 |

**输出一份可复跑的脚本，不是一次性 SQL。**

## 四、AI 测试方法（v2.1 修正）

**不再测"聪明"，只测四条硬线 + 一次人工盲评。**

| # | 硬线 | 判定 |
|---|---|---|
| 1 | 输出 schema 合法 | 100% 可解析，字段类型正确 |
| 2 | 模型不可用 | 停掉 Ollama，接口仍 200 且返回规则结果 |
| 3 | 超时降级 | 人为 sleep 8s，接口 10s 内返回模板文案 |
| 4 | 延迟 | **结构化结果 <1s；文案 <10s**（不是"首字 <2s"） |

**评测集（W8，50 条）**：20 条典型需求、15 条模糊需求、10 条无关需求（应引导而非硬推）、5 条对抗输入（超长、emoji、SQL 片段）。
**盲评**：5 个人对 Top5 结果打 1-5 分，均分 ≥3.5 视为可用。这是唯一能证明"推荐有没有用"的证据。

## 五、性能测试基线（v2.1 改三段式）

**必须记录硬件**，否则报告没有意义：

```
报告首页固定写：CPU 核数 / 内存 / JVM 参数 / MySQL 版本 / 是否同机部署 Ollama / 数据量
```

| 阶段 | 时点 | 内容 |
|---|---|---|
| **基线** | W9（不优化） | 单接口 QPS / P95 / 错误率，现状如实记录 |
| **优化** | W10 | SQL 索引、缓存、JVM、连接池 |
| **复测** | W10 | 同硬件同数据，报告写"P95 下降 X%" |
| **AI** | W9/W10 | 不按 QPS 压，压**并发 1/2/4 的响应时间曲线**（CPU 推理会排队，QPS 无意义） |

| 接口 | 目标（基线之上） |
|---|---|
| 登录 | P95 <300ms |
| 房源列表 | P95 <500ms |
| 房源详情 | P95 <500ms |
| 评分提交 | P95 <500ms |
| AI 结构化结果 | <1s |
| AI 文案 | <10s |

## 六、必测清单（v2.1 扩充）

| 类型 | 必测项 |
|---|---|
| 冷启动 | 0 评价房源展示分 = 4.0；3 条 5 星后趋近 5.0；列表显示"新上"标签 |
| 评价窗口 | 退租当天可提；第 30 天可提；第 31 天拒绝；无租约不可提 |
| 防刷 | 同一租约重复提交拒绝；未退租提交拒绝 |
| 状态机 | 5 状态 25 组合，20 条非法全 409；两房东并发接单只有一人成功 |
| 幂等 | 重复提交报修只生成一条；重复确认账单不重复记账；定时任务重跑不重复生成 |
| 越权 | 房东 A 访问 B 的房源/工单/账单 → 403；租客改他人评价 → 403 |
| 安全 | `' OR 1=1 --` 注入；上传 `.jsp/.php` 被拒；篡改 JWT 签名被拒；过期 token 被拒 |
| 金额 | 0.01 元、99999.99 元的边界；分/元换算不丢精度 |
| 时区 | 23:59 创建的租约，`actual_end_date` 不跨天 |
| AI 降级 | 停 Ollama / 超时 / 非 JSON 返回，三种情况都不 500 |
| 迁移 | 老库/新库/接口三方金额一致；老密码可登录 |

## 七、缺陷分级（v2.1 新增"数据类"）

| 等级 | 定义 | 响应 |
|---|---|---|
| P0 | 崩溃、数据丢失、**金额错账**、越权可写、AI 全挂 | 当天 |
| **P0-数据** | **评分算错、金额差 1 分、日期差 8 小时、状态错乱** | 当天（不崩不报错，但比崩更伤信任） |
| P1 | 核心流程不通（提交评价没反应、账单打不开） | 3 天 |
| P2 | UI 错位、文案错、边缘情况 | 本版内 |

Bug 单必含字段：编号 / 标题 / 指派人 / 状态 / 优先级 / **发现阶段**（开发自测 / 联调 / 回归 / 演示前）/ **是否必现**（必现 / 偶现 / 一次）/ 复现步骤。
没有"发现阶段"，W12 的缺陷逃逸分析就是空的；没有"是否必现"，偶现缺陷会在回归时被当成"已修复"放过去。
