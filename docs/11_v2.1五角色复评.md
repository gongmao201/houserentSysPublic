# 角色 A · 资深全栈架构师（复评）

## A.1 总体判断

**信心分 6.0 / 10**（上轮 3.0）。

**致命问题（新的，不是上一轮的）**

**A-新1：AI 在这次方案里实际上"没有部署位置"。**
v2.1 写：推荐拓扑 B（4C8G 云服务器）+ "AI 上线条件：≥32GB 才部署 Ollama"。这两句放在一起，结论只有一个：**线上没有 LLM。**
那么 3.1 节整章（意图抽取、LLM 兜底、推荐理由生成）和 3.1.1 节（embedding + cosine）在线上全部不成立，实际交付是"规则打分 + 模板文案"。
这不是错，是**没说清**。文档用大量篇幅写 AI，最后交付里没有 AI，W12 演示时老板问"模型在哪"，没人答得上。

**A-新2：BE 人日复算 57 vs 51，超载 12%。**
v2.1 砍掉的（jakarta 8 人日、bill 三表 3、Web 重写 7 分给 FE）与新增的（租约状态机 3、compose 2、监控 2、对账 3、造数脚本 2、越权补齐 1）前后抵消，净省不到 2 人日。
逐项：依赖+骨架 4 / Redis+JWT+OpenAPI+compose 5 / 迁移对账+XML 复查 7 / 评分 6 / 租约 3 / 报修 5 / 账单 5 / AI 6 / 越权+监控 4 / 安全整改 3 / 造数 2 / Bug 5 / 部署 2 = **57**。

## A.2 打分

| 维度 | 分 | 理由 |
|---|---|---|
| 技术选型合理性 | **4** | Boot 2.7.18 是对的选择；扣分在"AI 选型与部署拓扑互斥"没被承认 |
| 工作量估算合理性 | **3** | 砍得对，但新增项吃回去了，57 vs 51 仍未过 |
| 风险识别完整性 | **4** | 硬风险基本齐了；缺"AI 无部署位置""文档内部数字不一致"两类 |
| 用户体验提升幅度 | **3** | 4 页 + 大屏能打；8 页换肤效果存疑 |
| 可维护性 / 扩展性 | **5** | Flyway + OpenAPI + TS + tokens + 对账脚本，这套底子能传下去 |
| 上线可行性 | **3** | 能部署、能监控、能回滚；但小程序分发仍不通 |
| 测试覆盖充分度 | **4** | 快照 + 对账 + 三段式压测，架构上可测了 |

## A.3 硬伤

**P0**
1. **AI 双形态写清楚**：线上 = 规则 + 模板（无 LLM）；演示 = 演示机跑 3B（离线，不对外）。验收清单里加一条"线上无 LLM 依赖，`ai.mode=rule` 可跑通全部流程"。
2. **BE 57 人日**：再砍三项——① 3.1.1 的 embedding 层本期直接删（省 2）；② 账单定时任务改"手动生成 + 一个 cron"，省 1；③ 越权校验并入各模块开发不单列，省 1。降到 53，接受 4% 超载。

**P1**
3. 12 个 XML mapper 的 `test` 表达式复查，v2.1 提了但没排人日——实际是 1.5 人日体力活，要从别处挪。
4. `hrent_rent` 加 6 个字段 + 唯一索引，老代码的 `INSERT` 语句（17 条 INSERT 里可能有）会因非空约束失败，需检查。
5. 单库 JWT 迁移（删 java-jwt）后，老 token 全部失效——上线当天所有在线用户被踢。需双验一期。

**P2**
6. 统一响应体只在 v2 生效，前端会有两套解析逻辑，建议在 axios 拦截器里做一次归一，别散落在组件里。

## A.4 漏掉的

- **数据量增长后的索引失效**：60 套房时任何 SQL 都快，2000 套房时 `LIKE '%小区%'` 全表扫。压测必须用"未来半年"的数据量（建议 2000 套）造一次。
- **Flyway 与存量库的第一次握手**：老库已有 13 张表且有数据，Flyway `baselineOnMigrate=true` + `baselineVersion=0`（干净老库；已手动跑到 V6 的库用 6）必须配，否则启动直接报错。这条 v2.1 没写，是 W2 必踩。
- **时区一致性**：容器 `TZ`、JDBC `serverTimezone`、MySQL `time_zone` 三处必须同时改，缺一个就差 8 小时。

## A.5 替换建议

**R-A1　AI 分双形态，别硬凑一套。**
```
线上：ai.mode=rule        规则打分 + 模板文案（4C8G 可跑，延迟 <300ms）
演示：ai.mode=llm         演示机（32GB/或借一台游戏本）跑 3B，仅现场用
开关：application.yml 一行切换，前端无感
```
这样"老板要的 AI"在演示里真实存在，"线上不烧钱"也成立。**比现在这种"写了 AI 但部署不了"诚实得多。**

**R-A2　Flyway 基线配置写进 W2 交付物。**
```properties
spring.flyway.baseline-on-migrate=true
spring.flyway.baseline-version=0
spring.flyway.baseline-description=legacy-13-tables
```

| 动作 | 内容 |
|---|---|
| 砍 | 3.1.1 embedding、账单定时任务简化、越权单列 |
| 加 | W2 加"Flyway baseline 验证"（0.5 人日）；W10 加"2000 套数据量压测" |
| 并行 | 已是并行；补一条"BE 写接口 → QA 同步写对账"的结对，别再串行 |

## A.7 偏离

**需求 1（AI）在线上被完全替换为规则引擎。** v2.1 没说，本轮必须写明。

# 角色 B · 资深产品经理（复评）

## B.1 总体判断

**信心分 5.0 / 10**（上轮 3.5）。

**致命问题**

**B-新1：砍掉租客评分后，"双向评分"这条需求只剩一半。**
老板原话："官方评审 + 用户评审并存，帮房东筛租客、租客筛房东。"——**筛租客**这个动作的载体就是租客评分。一期砍掉，等于"租客筛房东"做了，"房东筛租客"没做。
这不是技术问题，是**承诺管理问题**：需求确认书里还写着"评分（房源+房东）"，老板不会自己意识到少了一半。必须主动说明，并给替代方案（见 R-B1）。

**B-新2：交付物仍然"不可分发"。**
v2.1 把"体验版"改成"预览二维码"，但开发者工具的预览二维码有效期只有约 25 分钟，扫完即废，**它不是一个可以交出去的东西**。
老板拿不到任何能自己打开的东西 → 他只能在你演示时看 → 一旦演示出问题，等于没交付。

## B.2 打分

| 维度 | 分 | 理由 |
|---|---|---|
| 技术选型合理性 | **4** | 从业务可交付性看，规则优先是对的；但"AI 只在演示存在"会让验收口径变窄 |
| 工作量估算合理性 | **3** | 功能粒度清楚了；造数 200 套仍写在 01（与 10 号清单的 60 套冲突） |
| 风险识别完整性 | **3** | 补了合规与死锁；仍缺"承诺落差"这一类风险 |
| 用户体验提升幅度 | **3** | 空态/加载/错误态 + 适老化 + 骨架屏是真提升；8 页换肤提升有限 |
| 可维护性 / 扩展性 | **4** | 申诉入口、冷启动标签、NEW 标记，这些都是产品级设计 |
| 上线可行性 | **2** | 仍无分发物，无真实用户，上线为 0 |
| 测试覆盖充分度 | **4** | 从"点一遍"升级到可判定，进步最大的一项 |

## B.3 硬伤

**P0**
1. **给"双向评分"换一个能兑现的叙事**：改叫「**房源双维评分 + 房东服务评分**」，并在需求确认书里写明"租客信用评分二期，需先建申诉机制"。**不要用"双向"这个词**，它会被追问。
2. **交付物必须可分发**：见 R-B2。老板手上要有一个"双击就能打开"的东西。

**P1**
3. 造数规模两份文档不一致（00/01 写 200，10 写 60）——W1 签字前必须统一为 60，否则 W9 验收时按 200 判负。
4. 评价维度（房源 5 维 / 房东 4 维）仍是拍脑袋。W2 找 5 个租过房的人各聊 20 分钟，半天成本，能省一轮返工。
5. "官方评审"这个词有误导：学生团队没有主体，"官方"是谁？建议改"平台核验"，并公开核验项。

**P2**
6. 房东回复权（对差评解释）没做，成本半天，对信任提升明显。
7. 逾期提醒只有站内信，租客不打开就永远看不到——建议加"账单生成时发一条一次性订阅"（用户点了才有，不点不追）。

## B.4 漏掉的

- **老板的验收场景**：他会怎么验收？大概率是"坐在你旁边看你点 10 分钟"。那交付物的核心不是代码，是**一条 10 分钟不出错的演示脚本**。v2.1 没有这份东西。
- **需求 3 的判据**：老板说"简陋空洞"，改完他凭什么说"不空洞了"？需要一张**改造前后对比图**（同一页面左右并排），这是最省力的说服工具。
- **失败预案**：演示当天 AI 超时、网络断了、数据没造好——三个场景各准备一句台词和一个降级演示路径。

## B.5 替换建议

**R-B1　用"房东筛租客"的轻量替代，别硬上信用分。**
一期给房东的是：**租客资料完整度 + 历史租约次数 + 是否有欠租记录（来自账单）+ 实名认证状态**。这四项不需要评分模型、不涉及对自然人的自动化决策、数据全部来自系统内部，且**真的能帮房东筛人**。
二期再上 1-5 星租客评分 + 申诉。

**R-B2　交付物改成"三件套"，别再纠结二维码。**
```
1) 演示录屏（3 分钟，1080p）—— 老板随时能看
2) 一键启动包：docker compose up -d + 一份 10 行 README —— 老板/评委能自己跑
3) 现场演示脚本（10 分钟，逐步骤 + 每步说什么）—— 你自己用
```
二维码作为"加分项"（能扫就扫，扫不了不承诺）。

**R-B3　做一张"前后对比图"。**
同一个房源列表页，左旧右新，W11 交付。老板对"UI 变好了"的判断，80% 来自这张图。

| 加 | W11 加"前后对比图 + 演示脚本 + 录屏"（2 人日，PM+QA） |

# 角色 C · 资深前端架构师（复评）

## C.1 总体判断

**信心分 7.0 / 10**（上轮 5.0）。前端是这轮整改受益最大的角色：范围清楚、技术路径正确、工具链补齐。

**致命问题**

**C-新1：8 个 view 的"换主题变量"被低估。**
12 个 view 里，那 8 个是老式"表格 + 弹窗 + 表单"结构，`<el-table>` 里大量硬编码 `style="color:#333"`、`width: 120px`、行内 `background:#fff`。只换 CSS 变量，视觉上仍是 2018 年的密度与间距。
两个选择，不能模糊：
- **A 只换变量**（2 人日）：观感提升 20%，风险低。
- **B 换变量 + 表格密度 + 间距 + 按钮尺寸**（5 人日）：观感提升 60%，但会碰布局。
v2.1 写"只换主题变量"，却在 W4 排了整整一周给 8 个 view——**自相矛盾**。

**C-新2：预览二维码这条路，前端也走不通。**
C 端的"交付"最终落在手机上。二维码 25 分钟失效意味着：**没有一个可持续访问的入口**。前端能做的只有"把 Web 做成一键可跑"，小程序侧必须承认"只能现场演示"。

## C.2 打分

| 维度 | 分 | 理由 |
|---|---|---|
| 技术选型合理性 | **5** | Vue3+TS+Element Plus+tokens+类型生成，教科书级；扣分在 8 页换肤的策略含糊 |
| 工作量估算合理性 | **4** | 4 页 + 大屏估得准；8 页低估 |
| 风险识别完整性 | **4** | SSE 半包、主包体积、tokens 漂移都识别了 |
| 用户体验提升幅度 | **4** | 三态 + 骨架屏 + 适老化是真提升 |
| 可维护性 / 扩展性 | **5** | 类型自动生成这一条，直接决定了这个项目明年还能不能改 |
| 上线可行性 | **3** | Web 可部署；小程序仍不可分发 |
| 测试覆盖充分度 | **3** | 前端仍无 E2E（Playwright 半天能加 5 条核心链路） |

## C.3 硬伤

**P0**
1. **8 页换肤二选一，写进 W4 DoD**：建议选 A（只换变量 + 表格 `size="small"` + 统一行高），2 人日封顶，省下的 3 人日给大屏和 E2E。

**P1**
2. 主包体积 W1 必须实测（现在 `miniprogram_npm` 是全量 Vant），若 >1.5MB，W2 就要做"按需引入 + 移除未用组件"，不能等到 W10。
3. Element Plus 按需引入的样式顺序会导致主题变量失效，建议显式引入 `element-plus/dist/index.css` + 覆盖变量，不用 unplugin 自动导入。
4. `openapi-typescript` 生成的类型会在 spec 变更时全部重写，`git diff` 噪音大。建议单独目录 + 单独 commit。

**P2**
5. 大屏用 ECharts 的 `dataset` 模式，别把数据写进 `series`，否则改一次数据要改代码。
6. 加 `Playwright` 5 条冒烟（登录/列表/详情/提交评价/提交报修），半天成本，能挡住"改了 A 页坏了 B 页"。

## C.4 漏掉的

- **老 Web 的全局 CSS 污染**：12 个 view 没有 scoped，换主题时会被老样式覆盖。迁移前先 `grep -c "^\." src/**/*.css` 看一眼规模。
- **小程序图片域名**：即使走预览，`<image src>` 指向的图片服务器域名也会被校验（图片域名同样要在白名单）。**这一条会让"预览模式"也显示不出图片**——必须在 W1 就确认，否则演示当天全是裂图。

## C.5 替换建议

**R-C1　8 页换肤降到 2 人日，只做三件事**：主色变量、表格 density、按钮/间距统一。不动结构、不动布局。
**R-C2　W2 加 Playwright 5 条冒烟**，与 QA 的 Newman 互补（一个测 UI，一个测接口）。

# 角色 E · 运维 / SRE 工程师（复评）

## E.1 总体判断

**信心分 4.5 / 10**（上轮 1.5）。改善明显：compose 提前、监控落地、回滚有演练。但有一个硬矛盾没解决。

**致命问题**

**E-新1：4C8G 跑不了 LLM，所以"AI 需求"在线上不存在。**
这不是 SRE 的锅，是方案没敢写结论。8-9GB 是"3B 模型 + 全套服务"的账，4C8G 连 3B 都放不下（4GB 内存给 OS + MySQL + JVM 已经紧）。
所以：拓扑 B 与"AI 上线"二者只能选一个。**建议选 B，并明说线上没模型。**

**E-新2：单机 = 没有灰度、没有高可用、备份无 RPO/RTO。**
v2.1 补了"备份策略"和"回滚演练"，但没定指标：
- RPO（能丢多少数据）：每日全量 → 最坏丢 24 小时。对租房系统可接受吗？账单数据丢一天就是错账。
- RTO（多久恢复）：单机重装 + 恢复 = 2-4 小时，不是 30 分钟。**"回滚 ≤30 分钟"只覆盖"代码回滚"，不覆盖"数据损坏"。**
这两个数必须写进运维手册，否则是自欺。

## E.2 打分

| 维度 | 分 | 理由 |
|---|---|---|
| 技术选型合理性 | **4** | 单体 + Compose + 托管云主机，对 5 人团队是最优；扣分在"AI 与业务同机"这个假想 |
| 工作量估算合理性 | **3** | 运维工作量仍压在 BE 身上（无专职 SRE） |
| 风险识别完整性 | **4** | 容量、成本、监控都补了；缺 RPO/RTO 与"谁值班" |
| 用户体验提升幅度 | **4** | 有监控意味着故障能被发现，这本身就是体验 |
| 可维护性 / 扩展性 | **4** | 向前兼容迁移 + 镜像 tag 回滚，是正确姿势 |
| 上线可行性 | **2** | 能部署，但分发与合规仍不通 |
| 测试覆盖充分度 | **3** | 压测改善；缺故障注入（停 Redis / 满磁盘 / OOM） |

## E.3 硬伤

**P0**
1. **明确 RPO/RTO**：RPO ≤ 24h（每日全量）+ binlog 可做到 ≤ 1h（若开启）；RTO：代码回滚 30 分钟、数据恢复 4 小时。**两个数写进运维手册，不要含糊。**
2. **AI 与拓扑二选一，写死**：线上 `ai.mode=rule`；演示机单独跑 `ai.mode=llm`，不接公网。

**P1**
3. 备份要**异地**一份（同一台机器上的备份等于没备份）。最小成本：对象存储 ¥5/月 或 另一台电脑 `rsync`。
4. 磁盘水位告警（>80%）——报修图片 + 日志最容易把 80G 打满，这条比"错误率"更早触发。
5. 无值班表。5 个人也要排，哪怕只是"演示前一周谁 on-call"。

**P2**
6. 日志 JSON 化 + `traceId` 前端可见（现在只在后端），否则用户报障说不清。
7. `docker compose` 加 `restart: unless-stopped` + `healthcheck`，机器重启后自愈。

## E.4 漏掉的

- **证书续期**：Let's Encrypt 90 天，谁续？忘记续 = 全站红锁。用 `certbot renew --dry-run` 加 cron。
- **带宽**：5M 带宽 ≈ 640KB/s，一张 200KB 图 = 0.3 秒/人，10 人同时看列表就卡。图片必须压缩 + 缓存头。
- **Ollama 模型持久化**：容器重建模型没了（4.7GB 重下）。挂 volume，写进 compose。

## E.5 替换建议

**R-E1　监控只做 4 个指标 + 1 个面板**：CPU、内存、磁盘水位、接口 P95；面板一页放完。别上全套。
**R-E2　备份三层**：本地全量（每日）→ 异地全量（每周）→ binlog（实时）。恢复演练时只演"本地全量 + binlog 回放到 1 小时前"。
**R-E3　演示环境与线上环境分离**：演示库固定快照，演示前 `docker compose down && up` 重置，2 分钟回到干净状态。

## E.6 排期

| 动作 | 内容 |
|---|---|
| 砍 | 高可用、CDN、灰度（本就没有） |
| 加 | W2 备份异地 + 证书自动续期；W10 磁盘水位告警；W11 数据恢复演练（不只代码回滚） |
| 并行 | compose 与业务开发同步维护，别让 compose 落后于代码 |

## 交付概率判断（本轮）

| 口径 | 概率 |
|---|---|
| 交付一个"能现场演示、10 分钟不出错"的系统 | **70%** |
| 交付一个"代码可交接、缺陷可复现、环境可重建"的工程 | **65%** |
| 交付一个"可分发、可自服务体验"的产品 | **15%** |
| 交付一个"可上线运营"的产品 | **0%（合规未通，非技术问题）** |

## 仍然存在的 4 个真问题（不修也能演示，但会被追问）

1. **线上没有 LLM** —— 用双形态解决，但必须在验收口径里写明。
2. **交付物不可分发** —— 用三件套解决，二维码只作加分。
3. **"双向评分"只剩单向** —— 改叙事 + 给房东侧的四项轻量信号。
4. **BE/QA 仍超载 4%–12%** —— 横向调剂 + 再砍 4 人日，仍需 W11 buffer。

## 需求偏离（第二轮）

| 需求 | 判定 | 与上轮对比 |
|---|---|---|
| 1 AI + RAG | **线上退化为规则引擎**，演示层有 3B 模型和轻量向量 | 上轮"部分弱化"，本轮**更清楚但也更弱** |
| 2 双向评分 | **单向（房源 + 房东）**，租客侧改为"资料完整度 + 欠租记录" | 上轮"结构完整不可运行"，本轮"可运行但少一半" |

## 一句话

> v2.1 把"做不到的事"从 20 条压到 4 条，这 4 条都不是技术硬伤，而是**口径问题**：线上没模型、交付不可分发、双向变单向、人日紧 10%。
> 把这四条**如实写进 W1 的确认书**，这个项目就从"必然翻车"变成"大概率能交出东西"。
> 反过来，如果继续用"AI 智能选房""双向评分""体验版分发"这些词对外汇报，W12 一定被打回。
