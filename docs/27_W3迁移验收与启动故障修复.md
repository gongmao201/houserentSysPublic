# W3 迁移验收与启动故障修复（2026-11-14）

> 范围：`hrent-api` 结构迁移（V1–V8）、回滚、三方对账、存量 INSERT 兼容、12 个老 mapper 复查、14 个老 Controller 冒烟、8899 实例启动故障定位与修复。
> 结论：**数据库闭环通过，103 个存量入口 0 失败；启动故障已定位并修复，8888 正式服务已恢复。**

## 1. 启动故障：根因与修复

### 1.1 现象

- 用 `house_rent_v8t` 起 8899，12 秒后健康检查 `000`。
- `logs/w3app.out`：`FlywayValidateException: Detected failed migration to version 2 ... run repair`。
- 换 clean 库后能起，但日志显示 `Tomcat started on port(s): 8888`——`HRENT_PORT=8899` 不生效。

### 1.2 根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | `house_rent_v8t.flyway_schema_history` 残留一条 `success=0` 的 V2 记录（早期把该库当测试库，Flyway 在已有表结构上重跑 V2 失败） | `installed_rank=3, version=2, success=0` |
| 2 | `application.yml` 里 `server.port: 8888` 是**硬编码**，没有读 `HRENT_PORT` | 8899 实例实际监听 8888 |
| 3 | `mvn test` 若指向脏库，同样被 Flyway validate 拦住，表现为 3 个 Spring 上下文用例 `Failed to load ApplicationContext` | 首次 `mvn test` 9 用例 3 错误 |

### 1.3 修复

| 修复 | 文件/动作 |
|---|---|
| 端口改为环境变量，默认 8888 | `src/main/resources/application.yml`：`port: ${HRENT_PORT:8888}` |
| 脏库历史修复 | `UPDATE house_rent_v8t.flyway_schema_history SET success=1 WHERE success=0`（该库结构已手工跑到 V8，等价于 Flyway repair） |
| 冒烟改用干净库 | 新建 `house_rent_smk`，由应用启动时 Flyway 从零跑 V1–V8（同时验证 V8 触发器能被 Flyway 解析） |
| 正式服务恢复 | `start.cmd` 拉起 8888，Flyway 自动补 V8；`house_rent` 现有 `14` 个触发器、`0` 条失败记录、版本 `8`，健康检查 `200` |

## 3. 17 条存量 INSERT 与新约束

| 结论 | 说明 |
|---|---|
| 非空约束不冲突 | 清空 V1 的 `INSERT IGNORE` 演示行后，17/17 全部成功；13 张老表"NOT NULL 且无默认值"的列只有主键 `id`，老语句都显式给了 id |
| 直接跑会 8 条主键冲突 | 冲突源是 V1 预置的同批演示 id（admin=1、dict=0/11..16、menu=100..），**不是约束问题**，是两条引导路径数据重叠 |
| 新字段缺口已由 V8 兜底 | 老语句只写 `money/deposit/start_time/end_time`；V8 的 14 个 `BEFORE INSERT/UPDATE` 触发器在"新字段为空"时用 `COALESCE` 补齐，实测五类新字段 `null_target` 全为 0 |

## 4. 12 个 XML mapper 复查（本轮新发现并修复）

| 缺陷 | 影响 | 修复 |
|---|---|---|
| 大量 `house_rent.xxx` 硬编码库名 | 换库/演练库跑不起来 | 12 个 mapper 全部改为不带 schema 的表名 |
| `UserDao` 未映射 `pwd_algo` | 双哈希读不到算法标识 | resultMap 补 `pwd_algo`，insert 用 `IFNULL(#{pwdAlgo},'md5')` |
| **`DictDao.get` 错用了分页 SQL**（`from sys_dict limit #{offset}, #{limit}`，没有 `where id`） | `/dict/get` 恒 500，`limit '0','0'` 语法错误 | 改为 `from sys_dict where id = #{id}` |
| 老数据 `del_flag=1`、mapper 过滤 `del_flag=0` | 存量行"查不到"，表现为 `/dict/get`、`/applyRent/get` 空指针 500 | 口径问题（非结构问题）：冒烟库统一把存量行 `del_flag` 归零后全部通过；上线前需确认 del_flag 语义或去掉过滤 |

## 5. 密码双哈希

| 项 | 实测 |
|---|---|
| 存量 MD5 | `MD5("123456")=e10adc...` 可校验 |
| 登录静默升级 | 首次登录后库里变为 `$2a$10$...`，`pwd_algo=bcrypt` |
| **本轮修复的缺陷** | `User.pwdAlgo` 字段默认值 `"md5"` 导致登录时"更新登录时间"的第二次 update 又把 `pwd_algo` 写回 `md5`（密码已是 BCrypt、算法还是 md5，二次登录必失败）→ 字段默认值改为 `null`，update 的 `<if>` 不再误写 |
| 测试 | `PasswordDualHashTest` 从 JUnit4 迁到 JUnit5（原来没被 surefire 执行），`TokenUtilsTest` 篡改用例改 payload 首字符（原来改签名末两位会偶发假通过），合计 12 用例全绿 |

## 8. 遗留与风险

| 级别 | 事项 |
|---|---|
| P0 | 老 mapper 的 `delete` 都是 `where 1 = 1` + `<if id>`：不传 id 会把整表 `del_flag` 置 1（冒烟首次就清空了 `sys_user`）。建议在 `BaseService.delete` 或各 Controller 入口加 id 非空校验 |
| P1 | `HouseResourceService.get` / `ApplyRentService.get` 未判空：查不到记录时直接 NPE。建议补 null 返回 |
| P1 | 存量 `del_flag` 语义需与业务确认（老脚本写 1、V1 seed 写 0、mapper 只认 0） |
| P2 | 冒烟中 33 个写入口未覆盖，需要种子数据 + 合法 payload 再跑一轮 |
