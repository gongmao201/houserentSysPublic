| D2 | Redis 7 自带 Vector Set 做 RAG | **Redis 只做缓存**；向量（若做）存 MySQL，Java 内 cosine | `VADD/VSIM` 是 Redis 8 才有；Redis 7 做向量要装 Redis Stack |

## 三、五大改造方向 · v2.1 落地方案

### 3.1 AI 智能选房（规则为主，LLM 解释）

```
租客输入（结构化表单 或 自然语言）
    │
    ▼
[意图层] 规则抽取优先
    ├─ 词典/正则命中：区域、预算、房型、标签（养宠/近地铁/朝南）
    ├─ 命中 ≥3 字段 → 直接进检索（<50ms，不调模型）
    └─ 命中不足 → qwen2.5:3b 抽 JSON（3-6s，超时降级关键词直搜）
    │
    ▼
[检索层] MySQL 结构化过滤（区域/价格/房型/状态=可租）→ 候选集通常 <500
    │
    ▼
[排序层] 规则打分
    score = 标签命中数×0.5 + 贝叶斯评分×0.3 + 新鲜度(30天内 +0.2)
    │
    ▼
[解释层] 模板优先，LLM 增强（异步，超时 5s 直接丢弃，不阻塞返回）
```

**延迟指标（v2.1 修正 D11）**：

| 指标 | 目标 | 说明 |
|---|---|---|
| 结构化结果返回 | **< 1s** | 不依赖模型，规则抽取即可满足 |
| 推荐理由首字 | < 3s（若走 SSE） | 单次 LLM 调用，3b 模型可达 |
| 推荐理由完成 | **< 10s** | 超时走模板 |
| 模型不可用 | 仍返回结果 | 规则排序 + 模板文案，**不允许 500** |

**模型**：默认 `qwen2.5:3b-instruct-q4`（约 2GB）；7b 需 ≥32GB 内存，列为可选（`ai.model.name` 一行切换）。

#### 3.1.0 AI 三级自动降级（v3 新增，D18）

```
用户请求
   │
   ▼
[第 1 级] 云托管 → 花生壳(vicp.fun) → 本机 Ollama (qwen2.5:3b)
   │  超时 3s / 连接失败 / HTTP 5xx
   ▼
[第 2 级] 云托管 → DeepSeek API (https://api.deepseek.com, OpenAI 兼容)
   │  超时 8s / 余额不足 / HTTP 5xx
   ▼
[第 3 级] 纯规则匹配（ai.mode=rule，零外部依赖）
   │
   ▼
返回 HTTP 200 + 结构化结果 + 推荐理由（模板或 LLM 生成）
```

**关键认知**：
- **花生壳 vicp.fun 域名不需要备案**——这条链路是"云托管服务器 → 花生壳服务器 → 你电脑"的服务器到服务器调用，**不经过小程序 request 合法域名校验**。备案是小程序前端调后端的要求，不是后端调外部 API 的要求。
- **花生壳免费版限制**：1 Mbps 带宽、1 GB/月流量、5 并发连接。课程演示调用频率低，够用；但单次大 JSON 延迟会高，所以超时设 3s。
- **DeepSeek 成本**：约 6 元/百万 tokens，课程演示调用量几乎为 0。可靠性远高于花生壳（腾讯云出口，不受家庭网络影响）。
- **第 3 级规则匹配**：完全在云托管 Spring Boot 内运行，保证任何时候接口都返回 200。

**配置项**（`application.yml`）：
```yaml
ai:
  mode: auto          # auto / local / deepseek / rule
  local:
    endpoint: https://xxx.vicp.fun    # 花生壳穿透地址
    timeout-ms: 3000
    model: qwen2.5:3b-instruct-q4
  deepseek:
    endpoint: https://api.deepseek.com/v1/chat/completions
    api-key: ${DEEPSEEK_API_KEY}
    timeout-ms: 8000
    model: deepseek-chat
  rule:
    enabled: true      # 第 3 级永远开
```

#### 3.1.1 RAG 的轻量实现（**本期不做，移二期**）

原计划给一个零组件的实现（MySQL 存 embedding + Java cosine，80 行）。**复评后砍掉**，原因：BE 复算 57 人日仍超载，这 2 人日换不来演示价值——60 套房源用标签规则排序，效果与向量召回无差异。

保留设计，二期再上（`house_embedding` 表结构如下，先不建）：

```sql
CREATE TABLE house_embedding (
  house_id     VARCHAR(32) PRIMARY KEY,
  model        VARCHAR(64)  NOT NULL,   -- nomic-embed-text
  dim          INT          NOT NULL,
  vec          VARBINARY(4096) NOT NULL, -- float32 序列化
  content_hash CHAR(32)     NOT NULL,    -- 描述变更才重算
  updated_at   DATETIME     NOT NULL
);
```

**对外表述**：一期 = "标签规则排序 + AI 解说"；RAG 向量检索列二期。不要在一期说"已经做了 RAG"。

```sql
CREATE TABLE house_embedding (
  house_id     VARCHAR(32) PRIMARY KEY,
  model        VARCHAR(64)  NOT NULL,   -- nomic-embed-text
  dim          INT          NOT NULL,
  vec          VARBINARY(4096) NOT NULL, -- float32 序列化
  content_hash CHAR(32)     NOT NULL,    -- 描述变更才重算
  updated_at   DATETIME     NOT NULL
);
```

Java 侧 `float[]` + cosine，候选集 ≤2000 条时单次 <20ms，代码约 80 行。**不装 Redis Stack、不装 Milvus、不引 Spring AI。**
排序层公式变为：`score = 标签×0.5 + 评分×0.3 + 新鲜度×0.2 + cosine×0.4`（权重可配）。

> 对老板的表述："RAG 用自研轻量向量检索实现，不引入第三方向量数据库，成本为零。"——术语保留，工程降级。

### 3.2 评分体系：房源双维 + 房东服务（补齐供给方与触发条件）

> **命名统一（v2.3）**：对外不再使用"双向评分"，统一为「**房源双维评分 + 房东服务评分**」。原"双向"含"租客被评分"，一期不做（见 ④），继续用旧词会在验收时被追问。

**① 平台核验分 = 上架审核（一次性）**

> "官方"改为"平台核验"：团队无公司主体，"官方"是谁说不清；改为"平台核验"并公开 8 项核验项，可信度反而更高。

| 项 | 判定 | 权重 |
|---|---|---|
| 照片真实（无水印、非网图） | 是/否 | 0.20 |
| 地址可核验（小区 + 楼栋） | 是/否 | 0.20 |
| 设施与描述一致 | 是/否 | 0.15 |
| 价格合理（同小区 ±30%） | 是/否 | 0.15 |
| 合同模板已上传 | 是/否 | 0.10 |
| 消防与安全（燃气/电路） | 是/否 | 0.10 |
| 押付规则明确 | 是/否 | 0.05 |
| 无历史投诉 | 是/否 | 0.05 |

得分 = Σ(命中权重) × 5，落在 0–5。一次录入长期有效，描述变更时重审。

**② 冷启动公式**

```
展示分 = (C × m + Σs) / (C + n)      C = 5, m = 4.0, n = 评价数
最终分 = official ? official×0.4 + 展示分×0.6 : 展示分×1.0
n < 3 → 列表显示"新上房源"标签，不显示低分
```

**③ 评价窗口靠"退租确认"触发（v2.1 新增，P0）**

```sql
ALTER TABLE hrent_house_renting
  ADD COLUMN status TINYINT NOT NULL DEFAULT 0 COMMENT '0生效中 1已到期 2已退租 3已解约',
  ADD COLUMN actual_end_date DATE DEFAULT NULL COMMENT '实际退租日（评价窗口起点）';

ALTER TABLE review ADD COLUMN lease_id VARCHAR(32) DEFAULT NULL;
ALTER TABLE review ADD UNIQUE KEY uk_reviewer_target (reviewer_id, target_type, target_id, lease_id);
```

流程：房东或租客任一方点"退租确认" → `status=2` + `actual_end_date` → 双方 30 天内可评（后端校验 `NOW() <= actual_end_date + INTERVAL 30 DAY`）。
**没有这一步，"仅租约结束后 30 天内可评"永远不触发。**

**④ 一期范围（v2.1 明确收敛）**

| 项 | 一期（W5） | 二期 |
|---|---|---|
| 房源评分 | 上架审核 + 用户评价 + 贝叶斯平滑 | — |
| 房东评分 | 上架资质审核 + 用户评价 | — |
| **租客评分** | **不做** | 有申诉工单后再做 |
| 申诉 | 评价可申诉，48h 处理 | 工单化 |

> 依据：《个人信息保护法》第 24 条，对自然人的自动化决策需可告知、可拒绝、可申诉。一期不做，比"做了但无救济"风险低。

**⑤ 房东侧替代信号（v2.3 新增，回答"怎么帮房东筛租客"）**

一期不做租客评分，但"筛租客"这件事必须有替代物。给房东 4 个可见字段，全部来自系统内部数据，不构成对自然人的评分：

| 字段 | 来源 | 展示形式 |
|---|---|---|
| 资料完整度 | 头像/手机/实名/工作信息填写比例 | 4 格进度条 |
| 历史租约次数 | `hrent_house_renting` 计数 | 数字 |
| 欠租记录 | 账单 `state=逾期` 计数 | 数字（0 显示"无"） |
| 实名状态 | `sys_user` 实名标记 | 已认证 / 未认证 |

**⑥ 房东回复权 + 申诉（v2.3 新增，各 0.5 人日）**

- 房东可对每条评价回复一次（100 字内），回复展示在评价下方——比"删除差评"更能修复信任。
- 评价可申诉，管理员 48h 处理，处理结果通知双方；申诉期间该条不计入均分。

### 3.5 性能与部署（先把机器算清楚）

**部署拓扑（v3 定稿，D17）**：

| 方案 | 配置 | 月成本 | 判断 |
|---|---|---|---|
| A 全本地 | 桌面机 i5-13500K + 16/32GB | 0 | 小程序连不上，只能局域网演示 |
| ~~B 4C8G 自维护云服务器~~ | 已废弃 | ~150-250 | 需自管 Nginx/HTTPS/证书/带宽 |
| **C 微信云托管（推荐）** | CloudBase Run 实例 + 内置 MySQL/Redis | 学生套餐 ~¥0-100 | **默认域名已备案，小程序前端直连合法** |
| D 本机 Ollama（仅 AI 推理） | i5-13500K 桌面机 | 0 | 通过花生壳 vicp.fun 暴露给云托管调用 |

**v3 部署架构**：

```
[小程序前端]
    │  HTTPS（云托管默认域名，已备案）
    ▼
[微信云托管 CloudBase Run]
    ├─ Spring Boot API 实例（2C2G 起步，自动伸缩）
    ├─ 内置 MySQL 8.0
    ├─ 内置 Redis 7
    ├─ 文件存储（云托管 COS 挂载，替代本地 /uploads）
    │
    │  服务器到服务器（不走小程序域名校验）
    ▼
[花生壳 vicp.fun 穿透]
    │
    ▼
[本机 i5-13500K + Ollama qwen2.5:3b]（仅 AI 文案生成，演示用）
    │
    │  第 2 级降级（公网 HTTPS）
    ▼
[DeepSeek API]（可靠兜底）
```

**为什么选微信云托管**：
1. **默认域名已备案**——小程序前端 request 合法域名问题一次性解决，不需要自己买域名、做 ICP 备案、配 HTTPS 证书。
2. **MySQL/Redis 内置**——不用自己 docker-compose 维护数据库。
3. **免运维 Nginx/证书**——云托管自动处理 HTTPS、负载均衡、日志。
4. **学生套餐**——CloudBase 有学生免费额度/低价套餐，成本远低于自购云服务器。
5. **本机 Ollama 保留**——演示"本地部署 Qwen"的能力仍然成立（通过花生壳），但日常调用走 DeepSeek 保证可靠性。

**AI 双形态（v3 改为三级自动降级，见 3.1.0）**：

| 级别 | 跑什么 | 用途 |

| 第 1 级 | 本机 Ollama qwen2.5:3b（经花生壳） | 演示本地部署能力 |
| 第 2 级 | DeepSeek API | 可靠兜底，成本极低 |
| 第 3 级 | 规则匹配 + 模板文案 | 任何时候都返回 200 |

## 五、图片存储（W6 前定稿）

- 本地磁盘 + Nginx 静态挂载 `/uploads`，Docker volume 持久化；不引 OSS（无预算）。
- **上传即压缩**：服务端压到 200KB 内（原图留档可选），列表用 400px 缩略图（`?w=400` 或预生成）。
- 容量账：**60 套房 × 5 图 × 200KB ≈ 60MB**，3 个月 <200MB。**不做压缩的话 500KB×5×60 = 150MB 起，且小程序流量翻倍。**
- Nginx 必配 `client_max_body_size 10m`（默认 1m 会直接 413）。

v2.1 不再承诺做不到的事：不提审、不灰度、不上向量库、不全量重写、不喊"首字 2 秒"。
