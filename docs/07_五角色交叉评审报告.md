# 角色 A · 资深全栈架构师

> 立场：这是一份"文档工程"优秀、"软件工程"不及格的方案。甘特图和接口契约写得像模像样，但迁移副作用、依赖兼容、存量数据契约三件事一件没算。

## A.1 总体判断

**信心分 3.0 / 10。**

### 致命一：迁移难度被系统性低估，且押在一个方差最大的任务上

F2 + F3：74 个 Java、12 个 XML mapper、14 个 Controller，依赖里躺着 6 个 JDK17 + Boot 3.2 下必炸或必换的组件。而 P1 出口（W4）要求"旧业务 API 在新栈跑通"——这是全项目方差最大的任务，被排在了最前面，用一个人、四周、零 buffer。

具体会炸在哪：

| 依赖 | 现状 | 在 JDK17 + Boot 3.2 下的真实后果 | 处置 |
|---|---|---|---|
| `jjwt` 0.9.1 | 在用 | 依赖 `javax.xml.bind.DatatypeConverter`，JDK11+ 已移除 → 登录链路 **运行时 NoClassDefFoundError** | 升 `jjwt-api/impl/jackson` 0.12.x，API 全改，签发/校验代码重写 |
| `mybatis-spring-boot-starter` 1.3.0 | 2016 年版本 | 不兼容 Boot 3 自动配置，`SqlSessionFactory` 装配失败 | 升 3.0.x，包路径与配置项变更 |
| `spring-tx` 5.3.9 | 硬编码版本 | 与 Boot 3.2 携带的 Spring 6.1 冲突，依赖仲裁可能降级 | 删掉显式版本 |
| `fastjson` 1.2.71 | 在用 | 反序列化 CVE（1.2.83 前有多个）+ JDK17 反射限制需 `--add-opens` | 换 Jackson，全量替换调用点 |
| `commons-httpclient` 3.1 | 2011 EOL | 无安全补丁 | 换 JDK HttpClient |
| `mysql:mysql-connector-java` | 旧坐标 | Boot 3 已换 `com.mysql:mysql-connector-j` | 换坐标 + 8.x 驱动 |

**半天 spike 就能确认的事，方案里一个字没有。** 没有 spike 就排 4 周，等于赌博。

### 致命二：存量数据契约三处冲突，全会污染业务逻辑

F4 + F6 + F7 合起来看，这不是三个小问题，是"现代化改造"最容易翻车的标准姿势：**schema 升了，语义没升。**

1. 金额 `DOUBLE(元)` vs 新约定"分（整数）"。迁移脚本必须 `ROUND(x*100)`，且要处理浮点残值（`1234.56` 存成 `1234.5599999` 的情况）。没有对账，账单金额会差几分钱——缴费模块最忌讳这个。
2. 密码 MD5 无盐。JDK 升到 17、框架升到 3.2，密码还是 MD5，这是本项目最讽刺的一处。改 BCrypt 需要"旧哈希兼容登录 + 登录成功后静默升级"的双写策略，方案零提及。
3. 租约时间 `VARCHAR(50)`。评分窗口"租约结束后 30 天内"要 `DATE` 比较和范围索引，字符串存日期做不到，且格式一乱全错。

**这三件事必须在 W2 出迁移脚本 + 回滚脚本 + 三方对账，否则 P2 的评分和缴费模块会建在流沙上。**

### 致命三（技术层面第三条）：评分模型跑不通

F4：`sys_user.role` 是 INT 单值。现实里"二房东自己也在租房"是常态。单值角色 → 同一个人不能既发房源又签租约 → 双向评分里"房东评租客"根本没有数据入口。

## A.3 硬伤

### P0（不改会失败）

**P0-A1　Redis 向量能力判断错误。**
00 文档 3.1 节原文："Redis 自带 Vector Set 能力，无需独立向量数据库"。事实：`VADD / VSIM` 是 **Redis 8.0** 才有的数据结构；Redis 7 要做向量检索必须装 **Redis Stack / RediSearch**，走 `FT.CREATE ... VECTOR HNSW`。按文档写的"Redis 7"开工，第一步就卡住。
三选一，W1 定死，并在文档里写清：
- **(a) 推荐**：embedding 存 MySQL `VARBINARY`，Java 内暴力 cosine。数据量几百到几千，毫秒级，代码 50 行，零新增组件。
- (b) Redis Stack 7.4 + RediSearch，明确写出 `FT.CREATE` 的维度 / 距离度量 / HNSW 参数。
- (c) Redis 8 + `VADD/VSIM`，接受新版本风险。

**P0-A2　依赖兼容清单缺失，W1 会卡三天。** 见 A.1 表格。W1 第一件事是半天 spike，产出"能升 / 要换 / 放弃"三列清单。不要边升边踩。

**P0-A3　存量数据契约三处。** 金额单位、密码算法、日期类型。W2 交付迁移脚本 + 回滚脚本 + 对账脚本（行数、金额汇总、抽样 100 行字段比对全部一致）。

**P0-A4　`sys_user.role` 单值角色撑不起双向评分。** 改 `user_role` 关联表（`user_id, role, scope_id`），或至少 `role` 改位掩码。同步迁移存量 3 类角色。

**P0-A5　后端排期超载。** 58 vs 51，砍法见 A.5。

### P1（不改会延期 / 体验差）

- **P1-A1　统一响应体 `{code,message,data,traceId}` 是 breaking change，没有 API 版本化。** 14 个 Controller 全改，老小程序若已发版在线会直接 500。必须 `/api/v1` 与 `/api/v2` 并存。
- **P1-A2　账单双轨。** 新建 `bill / bill_item / payment_record` vs 存量 `hrent_rent`（F5）。两套数据结构并存 = "在租管理"页与"账单"页对不上账。二选一。
- **P1-A3　MyBatis XML 12 个 mapper 的 `<if>` 动态 SQL 在 Boot 3 下的类型推断收紧**，`Integer` 判空条件需要逐个复查（`test="x != null and x != ''"` 对 Integer 会在某些版本抛异常）。这是体力活，要排进 W3。
- **P1-A4　无 GraalVM / AOT 计划，Docker 镜像基于 JRE 17 约 200MB+**，多阶段构建能压到 120MB。小问题，但 W12 才想就晚了。

### P2（建议优化）

- 引入 Spring AI 还是自研 Ollama client？**自研**。一个 `RestClient` + 两个 DTO 就够，Spring AI 目前的抽象层对"本地 Ollama + 自定义 prompt"没有增量价值，反而多一层版本耦合。
- 分页统一 `page/size` 可以，但建议加 `total` 与 `hasNext`，小程序上拉加载需要。
- traceId 别只用 Logback MDC，要能通过响应头回传给前端，否则用户报障时拿不到 traceId。

## A.4 漏掉的关键事项

1. **图片存储。** 00 文档 B8 自己写"无 OSS/CDN，本地路径存储，生产不可用"，但 12 周甘特图里**没有任何一周**做这件事。而 P2 要上：报修多图、评价图片、巡检拍照。三件事叠加，学生服务器磁盘两周就满，且换机即丢。W6 前必须定（本地 + Nginx 静态 或 对象存储）。
2. **并发与幂等。** 报修抢单、账单确认、评分重复提交——状态机只画了箭头，没有唯一索引、没有乐观锁、没有幂等键。两个房东同时点"接单"会怎样？文档没答。
3. **越权。** 只讲"JWT 带 token"，不讲授权。房东 A 能不能改房东 B 的房源 / 工单 / 账单？每一层都要 `owner_id` 校验。这是最常见的 P0 安全 Bug。
4. **数据备份与回滚演练。** Flyway 管 schema 不管 data，13 张表迁移没有备份策略、没有回滚演练、没有时限承诺。
5. **Ollama 失败路径。** 模型挂了 / 超时 / JSON 解析失败怎么办？方案只写"流式"，没写失败。必须：结构化结果先返回（不依赖模型），推荐理由异步补、失败走模板。
6. **演示数据。** 17 条种子数据（F10）。评分、推荐、账单在无数据时全是空壳。需要 200 套房 + 3 个月账单 + 50 条评价的种子脚本——**没排期，没人认领**。

## A.5 替换建议

**R-A1　Boot 3.2 → Boot 2.7.18 + JDK17（若半天 spike 清不干净那 6 个依赖）。**
老板要的是"性能优化"，不是 "Jakarta EE"。Boot 2.7.18 是最后一个 javax 分支，官方支持 JDK17，性能已远超 2.5.5/JDK8；迁移量从 10–12 人日降到 3–4 人日，`jjwt` / `mybatis` / `fastjson` 全部不用换，风险从"可能炸"降到"基本不炸"。等业务稳定、有第二个人能接手时再上 3.x。**这是这份方案里最能保命的一条。**

**R-A2　AI 不做向量库，做"结构化 + 标签规则 + LLM 文案"。**
理由不是"向量难"，是**问题本身不需要**：用户 query 一旦抽成 `{区域, 预算, 房型}`，剩下的"能养猫、近地铁"本来就是标签匹配——而库里已经有 `hrent_tag` 与 `hrent_tag_and_house` 两张表。用向量做标签匹配，不可解释、易幻觉、还要背一个组件的运维。
做法：前端结构化表单 → SQL 过滤 → 规则打分（`标签命中数×权重 + 评分×0.3 + 新鲜度`）→ LLM 只生成"为什么推荐这套房"，异步 SSE，超时走模板。省 4–5 人日，首字 <2s 自然达成。

**R-A3　缴费不新建三表，扩展 `hrent_rent`。** 已有 `payable_time / pay_time / tenant_id / state`，只缺明细项。加 1 张 `bill_item` 即可，`payment_record` 用 `pay_time + state` 表达。省 3 人日，历史数据不断层。

**R-A4　评分：官方分不做巡检，做"上架审核"。** 巡检要线下人力，学生团队没有。改成发布 / 月度首次上架时管理员按 8 项清单打一次分——触发点明确、有数据、成本从"持续巡检"变"一次性审核"。

# 角色 B · 资深产品经理

> 立场：技术问题都能修，产品逻辑问题要命。这套评分体系在第一天就会死，因为没人给它喂分。

## B.1 总体判断

**信心分 3.5 / 10。**

技术交付都能靠加班补，产品交付不能。这 5 条需求里，有 3 条在方案中已经"结构完整但逻辑不可运行"。

### 致命一：评分体系没有供给方，也没有破局设计

方案写得很完整：`house_rating` / `landlord_rating` / `tenant_rating` / `review` / `official_inspection`，5 张表，加权公式 0.4/0.6。但三个问题没有一个被回答：

1. **官方分谁给？** "管理员后台新增巡检任务模块，支持拍照+清单打分"——谁去巡检？巡检一个房源要多久？学生团队有几个人能到现场？真实的答案是 0 人。`official_score` 会永久为 NULL。
2. **用户分谁给？** 评价窗口是"租约结束后 30 天内"，而系统里的租约（`hrent_house_renting`，F6）没有状态、没有结束事件、时间是 `VARCHAR`。**系统根本不知道租约什么时候结束**，这个窗口永远不会被触发。
3. **冷启动怎么办？** 双边市场死锁：没评价 → 租客不信 → 不下单 → 更没评价。方案里没有任何种子评价、官方背书、新盘加权曝光的设计。

三条叠加的结果：上线后所有房源 `score = 0×0.4 + 0×0.6 = 0`，或者被"无评价不显示评分"藏起来——**老板点开任何一个房源，看到的都是"暂无评价"**。这一条需求直接归零，而且是在 W12 演示当天才被发现。

### 致命二：缴费被降级成"催缴记账"，但需求写的是"加功能：缴费"

降级本身是对的、诚实的（无商户号确实接不了微信支付）。问题在两点：

1. **没有 W1 拿老板签字。** PM 文档把"和老板确认微信支付二期"排在 **W7**。W7 是缴费模块开发周，老板一句"我要能收钱"，前 6 周白干。这个确认必须在 W1，与需求确认书一起签。
2. **交付物命名与老板预期错位。** 老板要的是"缴费"，交付的是"账单 + 租客自己点已缴 + 房东确认"。价值是"催缴工具"，不是"支付"。这个错位必须在需求确认书里写清楚，否则 W12 验收时是"你没做缴费"。

顺带一个细节错误：文档写"逾期自动提醒（小程序订阅消息）"。小程序订阅消息是**一次性授权，一次只能推一条**，长期订阅类目不含租房。这个"自动"做不到。

### 致命三：UI 重做没有设计资产，交付物必然是"换了个主色"

老板的原话是"简陋空洞需重做"——这是**视觉问题**。方案的回应是：主色 #0B6EF8、辅助色 #FF9500、圆角 8px/16rpx、正文 14px/32rpx。

这叫设计规范，不叫设计。**没有线框图、没有页面级视觉稿、没有间距与层级的推敲、没有空状态/加载态/错误态的插画。** 团队里没有设计师，这份工作被隐式分给了"小程序开发"（05 文档 W1："输出新设计规范"）。一个开发用 5 个色值定义出来的"设计系统"，做出来的东西和现在不会有本质区别。

老板验收时会说："还是那个后台，就是变蓝了。" 这句话一旦说出口，这条需求就不算交付。

## B.3 硬伤

### P0（不改会失败）

**P0-B1　评分体系缺"供给"设计，必须补三件事：**
1. **官方分改"上架审核一次性打分"**：房源发布时管理员按 8 项清单打分（照片真实性、地址可核验、设施齐全、价格合理性、合同模板、消防、押付规则、历史投诉）。触发点明确，不依赖巡检人力。
2. **冷启动降级公式**：`score = (C×m + Σs)/(C+n)`，m=4.0（先验），C=5（平滑强度）；`official` 为 NULL 时权重回落为 `user 1.0`，**不许用 0 参与加权**。同时"评价数 < 3"的房源在列表页显示"新上房源"标签而非低分。
3. **种子评价**：W9 前造 50 条真实评价（团队自己走完 20 单完整租约流程，含退租确认），这是演示能不能看的前提。

**P0-B2　租约没有"结束"这个事件，评价窗口无法触发。**
`hrent_house_renting`（F6）只有 `start_time / end_time` 两个字符串，没有状态机、没有 `actual_end_date`、没有"退租确认"动作。产品规则必须先补：租约加状态（生效中 / 已到期 / 已退租 / 已解约）+ `actual_end_date DATE`，由房东或租客任一方点"退租确认"落库，**这个动作才是 30 天窗口的触发器**。没有这一步，"仅在租约结束后 30 天内可评"是一句无法执行的规则。

**P0-B3　缴费的交付口径必须在 W1 书面确认。** 需求确认书里写清楚："一期交付账单生成、租客标记已缴、房东确认到账、逾期提醒；不含在线支付。" 老板签字。W7 才确认 = 赌博。

**P0-B4　UI 必须有设计资产。** W1 出 6 张关键屏视觉稿（小程序首页/详情/AI 选房/账单、Web 登录/数据大屏），W2 冻结，**冻结前开发不许写 UI 代码**。没有这一步，需求 3 一定被判定为未交付。

### P1（不改会延期 / 体验差）

- **P1-B1　差评无申诉。** 租客被房东打低分且"仅在房东端可见"，会影响后续申请通过率——这是对自然人的自动化决策（《个人信息保护法》第 24 条：需告知、可拒绝）。"管理员可隐藏"是掩盖不是纠错。加一条申诉工单，成本一天，法律风险归零。
- **P1-B2　AI 没有可测的价值指标。** 老板问"AI 到底有没有用"，方案答不出。必须定义 3 个指标：意图抽取字段准确率 ≥80%、Top5 相关率（人工标注）≥70%、首字 <2s。W8 出基线，W9 出对比。
- **P1-B3　评价维度是拍脑袋定的。** 房源 5 维（装修/位置/性价比/房东配合度/噪音）、房东 4 维（响应速度/维修及时性/押金退还/沟通态度）。没有一条来自真实租客访谈。至少找 5 个租过房的人各聊 20 分钟，把这 9 个维度验一遍——这是半天成本，能省掉一整轮返工。
- **P1-B4　"官方评审"的信任来源不清。** 打"官方"两个字，用户会认为是平台背书。学生团队没有主体，"官方"是谁？建议改叫"平台核验"或"实地核验"，并把核验项公开（让用户看到核验了什么），可信度反而更高。

### P2（建议优化）

- 房东分权重 0.3/0.7 比房源分更偏用户——合理，因为房东服务质量的主观性更强。这个设计是对的，保留。
- 评价支持图片，但要限 3 张 + 压缩，否则存储和审核都是坑。
- 加分项：租客分只在房东端可见，这个隐私设计是对的，但要加一句"租客可查看自己的分数与构成"，否则是黑箱。

## B.4 漏掉的关键事项

1. **内容供给。** 一个租房平台没房源就没一切。现在是 17 条种子数据（F10）。谁去造 200 套房？图片从哪来（不能用别人的真实房源图，有版权和真实性风险）？这件事没有 Owner。
2. **用户获取。** 12 周计划里没有一个字讲"谁来用"。业主从哪来？租客从哪来？哪怕是课程作业，也要写清"演示用户从哪来"。
3. **审核合规。** 小程序要隐私政策 + 用户协议 + 个人信息收集清单（手机号、openid、位置、照片）。没有这些，提审直接拒。文档零提及。
4. **验收标准不可测。** 7 项 KPI 里 4 项不可测："UI 好看""智能""体验提升""性能优化"。不可测 = 不可验收 = W12 扯皮。
5. **差评的业务后果没设计。** 房东被差评后能不能继续发房源？租客被差评后能不能继续申请？没有处置规则，评分只是装饰。
6. **老板的真实诉求。** 5 条需求里，"AI"和"评分"更像"要有故事可讲"，"UI"和"性能"更像"看起来不像学生作业"。如果这是毕设/路演，方案应该把"可演示性"排在"可运营性"前面——现在的方案两头不靠。

## B.5 替换建议

**R-B1　评分从"体系"降级为"可信信号"，先做能跑的。**
一期只做三件事：房源上架审核分（8 项清单）、租约结束后的用户评价（1-5 星 + 文字 + 3 图）、房东回复权。不做租客评分（法律风险 + 无数据 + 无申诉机制）。二期再上租客分与加权公式。
理由：一期做"能显示、能看懂"的评分，比做"公式很漂亮但全是 0"的评分有价值 10 倍。

**R-B2　AI 的价值主张改成"解释型推荐"，不赌"更准"。**
规则排序 + LLM 解释的准确率不会比纯规则高，但**"AI 告诉你为什么推荐这套房"这个体验是新的**，且天然可解释、可演示、可验收（用户能不能看懂那句话）。把 KPI 从"推荐准确率"改成"推荐理由可读性评分（5 人盲评 ≥3.5/5）"——这个能测，也确实是用户价值。

**R-B3　缴费改名"账单中心"，并在 UI 上把"线下转账"讲清楚。**
租客看到"标记已缴"四个字会困惑。改成三步引导：①查看本期账单 → ②按房东收款方式转账 → ③上传凭证并标记。房东端给"待确认"队列 + 一键确认。这个流程本身就是产品价值（把微信里的转账记录变成可追溯的账）。

**R-B4　UI 用"抄 + 改"而不是"设计"。**
没有设计师就不要假装有。W1 直接拿贝壳/自如/闲鱼租房的截图，逐屏对齐：间距、字号层级、卡片结构、按钮位置。允许"像"，不允许"空"。这比自创设计系统快 3 倍，且老板一眼能看出"专业了"。

# 角色 C · 资深前端架构师

> 立场：前端不是瓶颈，但方案把前端的账算错了——量算多了（Web），技术基线写错了（小程序），最难的那块（SSE）只写了四个字。

## C.1 总体判断

**信心分 5.0 / 10。** 五个角色里最高。理由：前端工作量被高估了，真正难的技术点只有一个（小程序流式），而它被严重低估。

### 致命一：小程序技术基线写错了，重写策略会撞墙

F9：小程序实际用 **@vant/weapp**（`miniprogram_npm` 里有完整构建产物，含 button / cell / field / popup / uploader / skeleton 等 60+ 组件），而 05 文档技术基线写"UI 基础：WeUI + 自定义设计系统（不直接用 WeUI 默认灰）"。

**用错了组件库，重写策略就会错。** 文档说"重写 wxss + 新增 6 个页面"。如果页面里全是 `<van-cell>`、`<van-field>`、`<van-uploader>`，你在页面 wxss 里写 `.cell { ... }` 是打不进去的——Vant 组件的样式封装在组件内部，必须：
- 通过 `--van-*` CSS 变量覆盖主题（`--van-primary-color`、`--van-cell-font-size` 等），
- 少数需要用 `externalClasses` 或 `:deep()` / `!important` 硬覆盖，
- 还有一部分（如 `van-button` 的 size/round）只能靠属性，不能靠样式。

正确做法不是"重写 wxss"，是"**定一套 `--van-*` 变量表 + 禁用默认灰 + 逐页替换布局容器**"。这条差别是 3 天和 10 天的区别。

顺带：文档说"老小程序 13 个页面结构合理"，实际只有 **6 个 wxml**（`pages/index/index`、`pages/index/search`、`pages/index/houseInfo`、`pages/userInfo/myInfo`、`pages/userInfo/collection`、`pages/logs/logs`）。基数错了，工作量估算的锚点也错了（往多了估，但方向性判断也因此失真）。

### 致命二：小程序流式只写了四个字，实际是前端最贵的一块

05 文档 W8 写："流式输出（`wx.request enableChunked`）、推荐理由打字机"。这四个字背后是：

1. `enableChunked` 需要基础库 **2.20.2+**，要写兼容降级（低版本直接非流式）。
2. 拿到的不是 `EventSource`，是**分块 ArrayBuffer**。要自己 `TextDecoder` 解码 + 按 `\n\n` 切 SSE 事件 + 处理**半包**（一个 UTF-8 汉字被切在两个 chunk 之间会变乱码，必须先拼 buffer 再解码，不能逐块 decode）。
3. 要处理 `data: [DONE]`、心跳、错误帧、中途断流的重试。
4. Nginx 必须 `proxy_buffering off; proxy_read_timeout 300s;`，否则流被缓冲成一次性返回——这个坑后端和运维都得知道。
5. iOS/Android 的 `wx.request` 分块行为有差异，必须真机验证。

**保守 2 人日，且必须有一个降级方案兜底。** 文档把它塞进 W8 一周里，和"AI 选房页整页开发"并列。

### 致命三（前端视角）：双端设计 tokens 没有单一来源，必然漂移

04 文档写 FE 从 MP 拿"统一设计规范（色板、组件命名）"，05 文档写 MP 给 FE"设计稿参考"。两份文档互相指，没有一个人是 owner。实际结果是：Web 用 `#0B6EF8`、小程序用 `#0B6EF8`，但间距一个 24px 一个 32rpx，圆角一个 8px 一个 16rpx，字号一个 14px 一个 32rpx——看起来像同一个品牌，细节全不一致，而且改一次要改两个仓库。

## C.3 硬伤

### P0（不改会失败）

**P0-C1　小程序基线改对：Vant Weapp，不是 WeUI。**

**P0-C3　设计 tokens 单一来源。**

**P0-C4　Web 不重写全部 12 个 view。**
F8：`src` 只有 25 个文件、12 个 view。其中真正影响老板观感的是 4 个：登录、房源管理列表、房源详情、数据大屏。其余 8 个（字典、菜单、图片、用户、约看审批、租房审批、在租、租约记录）保留 Element UI 结构，只换主题变量 + 修间距。省 7 人日，且降低"重写引入新 Bug"的风险。

- **P1-C1　暗色模式砍掉。** Element Plus 的暗色不是开关：要 `html.dark` + 覆盖 `--el-*` 变量 + 逐个自查自定义组件里的硬编码色（老项目 12 个 view 里全是 `#fff` / `#333`）。成本 3 人日，老板没要求，纯负债。
- **P1-C2　高德热力图砍掉。** 需要 key、需要域名白名单（又是备案问题）、需要配额，管理端看热力图没有决策价值。用 ECharts 散点图替代，0 成本。
- **P1-C3　响应式只做 1440 一档。** 管理端固定桌面使用，1366/1920 双断点是自我感动。用 `min-width: 1280px` + 弹性栅格即可。
- **P1-C4　小程序不要引 mobx-miniprogram。** 6 个页面 + 少量全局状态，`globalData` + 页面级 `setData` 足够。引状态库 = 多一层调试成本，收益为零。
- **P1-C5　Element Plus 按需引入别用 unplugin 自动导入的默认配置。** 它的样式副作用会导致暗色/主题变量顺序错乱。显式 `import 'element-plus/theme-chalk/dark/css-vars.css'` 更可控。

### P2（建议优化）

- 图表保留 ECharts 5，别为了"现代"换库（ECharts 5.3 已经是当前版本，没有升级收益）。
- 首屏 <300KB 对管理端意义不大（内网/办公网），这个 KPI 可以降级为"<500KB"。
- 加一条：所有接口必须有 loading 与 error 态，禁止"点了没反应"。这是小程序端的头号体验问题。
- `wx.request` 封装要带**请求去重**（同一接口 300ms 内重复调用合并），否则首页三个组件同时请求房源列表会打三次。

## C.4 漏掉的关键事项

1. **老 Web 的 CSS 遗产。** 12 个 view 里的样式是全局污染式的（没有 scoped），迁移时如果直接复制模板，会把污染带进新工程。要么全部重写样式，要么加 scoped 后逐页修。这条没排期。
2. **小程序分包的真实边界。** 主包 <1.5MB 的前提是 Vant 组件按需引入 + 图片全走 CDN。现在 `miniprogram_npm` 里是**全量 60+ 组件**，主包很可能已经接近上限。W10 才做分包太晚，W4 就要量一次主包体积。
3. **图片体积。** 房源列表图不压缩 + 不走 CDN = 小程序流量爆炸 + 首屏 3 秒。必须：上传时后端压缩到 200KB 内 + 列表用 `?x-oss-process=image/resize,w_400`（或本地缩略图）。
4. **真机矩阵。** iOS + Android 各 2 台，团队有没有这 4 台机器？没有的话"真机兼容报告"是编的。
5. **前端可观测。** 前端报错（白屏、接口 500）现在只能靠用户截图。最小方案：`window.onerror` + `unhandledrejection` 上报到一个 `/api/log` 接口，20 行代码。
6. **TS 严格模式的成本。** 12 个 view 从 JS 迁 TS，接口响应类型全要手写 interface（没有 OpenAPI 生成器）。文档说"不允许 any 糊弄"，那就得排 3 人日写类型 —— 或者上 `openapi-typescript` 自动生成（推荐，半天）。

## C.5 替换建议

**R-C1　小程序改造从"重写 wxss"改为"Vant 主题化 + 布局重构"。**
`app.wxss` 里 30 行变量覆盖，搞定 60% 的视觉改造；剩下 40% 是布局（间距、卡片结构、信息层级），逐页改。成本从 10 天降到 4 天，且组件行为不变、Bug 风险最低。

**R-C2　SSE 双轨：默认非流式 + 打字机，SSE 作为增强。**
理由：AI 生成本来就要 3-8 秒，用户感知的"流式感"来自文字一个个出现，不来自 TCP 分块。前端定时器渲染 30ms/字，视觉上和真流式没有区别，但零协议风险、零兼容问题、零 Nginx 配置。**这是性价比最高的一条前端决策。**

**R-C3　`openapi-typescript` 自动生成类型。**
W2 OpenAPI 冻结后，一条命令生成 `types/api.d.ts`，FE 直接用。省 3 人日手写 interface，且接口变更时类型自动跟着变（编译期就能发现 breaking change）。这比"红线：不允许 any"有效得多。

**R-C4　Web 只重写 4 页 + 统一主题变量。**
登录、房源列表、房源详情、数据大屏。其余保留结构换皮。老板 90% 的观感来自这 4 页（其中大屏占一半）。

# 角色 D · 资深测试 / QA 负责人

> 立场：这份计划里没有一行是"可验证"的。所有验收标准都停在"跑通了""达标了"，没有一条能被复现。

## D.1 总体判断

**信心分 2.0 / 10。** 五个角色里最低。

不是我悲观，是这份计划里**没有一条验收标准可以被第三方独立复现**：

- "AI 选房 demo 可跑通"——跑通什么？输入什么，输出什么算对？
- "压测报告达标"——达标线是 100 QPS，但没说压在什么硬件上。
- "所有用例通过"——用例在哪？多少条？谁写的？
- "UI 走查清单全 ✅"——清单谁定的？"✅"的标准是什么？

QA 的存在意义是把"做好了"翻译成"这样算做好了，这是证据"。这份计划把这个翻译工作整个跳过了。

### 致命一：没有回归基线，W4 的"老功能回归通过"是句空话

F2：14 个 Controller、13 张表、12 个 XML mapper。老系统**没有任何现存用例、没有接口快照、没有测试数据**。

W4 要求"旧业务 API 在新栈跑通 / 所有旧接口回归通过"。没有基线的话，这个"通过"只能是"人点了一遍没报错"。而迁移类项目最典型的缺陷恰恰是"点了没报错但数据不对"：金额少了 1 分、日期少 8 小时（时区）、分页 total 差 1、关联查询少一条。

**这三个坑（金额精度、时区、分页 total）在迁移项目里的出现率接近 100%，而"人点一遍"一个都发现不了。**

### 致命二：数据迁移不可验证

F4 + F6 + F7 三类迁移：`DOUBLE(元) → BIGINT(分)`、`MD5 → BCrypt`、`VARCHAR 日期 → DATE`。每一类都需要"迁移前后对账"，而计划里一个字没有。

具体风险：
- 金额：`1234.56 × 100 = 123455.99999` 取整成 `123455`，少 1 分。200 套房 × 12 个月账单 = 2400 条记录，错 1 分就是错账。
- 密码：MD5 转 BCrypt 若直接覆盖，所有老用户登录失败。必须"兼容旧哈希 + 登录时静默升级"，这个策略要写进用例。
- 日期：`VARCHAR '2026-11-03 00:00:00'` 转 DATE，丢时分秒；如果原数据有 `'2026/11/03'` 这种格式，直接转换失败。

**没有对账脚本，这三类迁移的验收只能靠"看起来对"。**

### 致命三：AI 测试没有方法，且目标不可测

- "意图抽取准确率"——分母（标注集）不存在。没有 200 条人工标注的 query，准确率无法计算。
- 流式测试——Postman 不支持 SSE 断言，Apifox 支持有限，需要写脚本。计划里没提工具。
- 模型非确定性——同一输入两次输出不同，"预期结果"怎么写？只能测契约（schema 合法、超时兜底、降级路径），不能测内容。
- "AI 首字 <2s"——这个可测，但与架构矛盾：意图抽取是一次 LLM 调用（3-6 秒），推荐理由是第二次调用。**首字必然 >3s。** 目标与设计不自洽。

### 致命四：压测目标与硬件不匹配，结论无法指导决策

QA 文档定的目标：登录 100 QPS / 房源列表 200 QPS / 详情 150 QPS，P95 <300-500ms。

问题：
1. **没有硬件基线。** 200 QPS 在 2C4G 上和在 8C16G 上是两个世界。报告写"达到 200 QPS"但不说机器，等于没说。
2. **学生机大概率跑不到。** 单机 MySQL + Redis + JVM + Ollama 同跑，2C4G 下房源列表能到 50 QPS 就不错。
3. **AI 接口不能按 QPS 压。** 20 并发对 CPU 推理 = 20 个请求排队，P95 会是分钟级。这条应该压"并发 1/2/4 的响应时间曲线"，不是 QPS。
4. **压测在 W10，优化也在 W10。** 同周压测同周优化 = 没有基线对比，无法证明"优化有效"。

### 致命五：灰度是伪概念，上线风险无兜底

单机部署、无负载均衡、无流量切分能力 → "灰度 10% 租客"物理上做不到。而且没有真实租客，10% 是多少人？

对应的真实问题是：**上线出问题怎么回滚？** 回滚脚本排在 W12 才写，且从未演练。

## D.3 硬伤

### P0（不改会失败）

**P0-D1　W2 之前必须建"回归基线"，否则 W4 无法验收。**
最小可行方案（1.5 人日）：
- **接口快照**：对 14 个 Controller 的 40+ 接口，各录一份"请求 + 响应 JSON"存入 `tests/snapshots/`（老系统跑一遍即可）。
- **冒烟脚本**：Newman（Postman CLI）+ 30 条核心链路，W2 起每天跑一次，红即告警。
- **迁移后逐条比对**：新栈跑同样请求，diff 快照，允许的差异（traceId、时间戳）白名单化，其余必须一致。
没有这个，W4 的"老功能回归通过"是主观判断。

**P0-D2　数据迁移必须有对账脚本，三类都要。**
- 金额：`SELECT SUM(money*100) 老库` vs `SELECT SUM(amount_fen) 新库`，必须相等；再抽样 100 行逐字段比。
- 密码：迁移后所有用户能用原密码登录（用 5 个测试账号验证），且 DB 里已是 BCrypt 格式。
- 日期：`COUNT(*) WHERE DATE(end_time) IS NULL` 必须为 0；再抽样比对 20 条。

**P0-D3　AI 验收标准改为"契约 + 兜底"，不测"聪明"。**
可测的三条：
1. 输出 schema 合法率 100%（JSON 能被解析、字段类型正确）。
2. 模型不可用 / 超时 5s 时，接口仍返回结果（降级到规则排序 + 模板文案），**不允许 500**。
3. 首字延迟：**如实写"意图抽取 3-6s + 文案 2-4s"**，KPI 改成"总时长 <10s，首字节（结构化结果）<1s"。现在写的"首字 <2s"与两次 LLM 调用的架构矛盾，必然不达标。

**P0-D4　压测改为"基线 → 优化 → 对比"三段式，且必须记录硬件。**
- W9 出**基线**（不优化，先测现状）：单接口 QPS、P95、错误率 + 机器规格。
- W10 优化后**同条件复测**，报告写"提升 X%"。
- AI 接口不按 QPS 压，压"并发 1/2/4 的响应时间曲线"。
- 报告首页必须写：CPU 核数 / 内存 / JVM 参数 / MySQL 版本 / 是否同机部署。

### P1（不改会延期 / 体验差）

- **P1-D1　越权用例缺失。** 房东 A 用 B 的 token 改 B 的房源、查 B 的账单、接 B 的工单——这三条必须有用例，且是 P0 级。这类 Bug 在毕设项目里 100% 存在。
- **P1-D2　状态机的非法跳转要穷举。** 报修 `CREATED → ACCEPTED → ON_SITE → COMPLETED → ACCEPTED_BY_TENANT`，5 个状态 = 25 种组合，合法 5 条，其余 20 条必须全部拒绝。文档说"覆盖 100%"，但没给组合矩阵。
- **P1-D3　幂等与并发用例。** 同一评价提交两次、两个房东同时接单、账单确认重复点击。这三条现在没有用例。
- **P1-D4　真机矩阵先确认资源。** iOS + Android 各 2 台，W1 就要确认有没有。没有就改"1 iOS + 2 Android 覆盖主流机型"，并写清型号。
- **P1-D5　缺陷分级缺"数据类"。** 现有 P0 定义里有"缴费错账"，但"评分算错""金额差 1 分""日期差 8 小时"这三类应单列，因为它们不会崩、不会报错、但会让系统失去信任。
- **P1-D6　手册砍量。** 用户手册 2 册 + 运维手册 1 册 = 10 人日。改：用户手册 1 册（租客版），房东版用 3 分钟录屏替代；运维手册由 BE 出稿、QA 只审。

### P2（建议优化）

- 用例模板可以用，但建议直接上 `testcase.md` + 标签（`@smoke @rating @ai`），方便筛选执行。
- Bug 看板用飞书多维表格可以，但要加"发现阶段"字段（开发自测 / 联调 / 回归 / 灰度），否则无法分析缺陷逃逸。
- 加一条红线：**"W11 之后不接受新需求"**，现在是 W12 还在做功能。
- 测试环境要独立于开发环境，且数据可一键重置——BE 文档提了"测试数据必须可重置"，很好，要有脚本。

## D.4 漏掉的关键事项

1. **无自动化框架选型。** 全文档 0 处提到 Playwright / Cypress / Newman / JMeter 的具体方案。QA 一个人手工测 6 个模块 × 3 轮回归 = 不可能。
2. **无测试数据管理。** 前置条件怎么写？"存在一个已完成租约的租客"——这个数据怎么造？谁造？怎么清？
3. **无缺陷逃逸分析。** 上线后发现的问题，怎么归因？没有"发现阶段"字段就没有改进依据。
4. **无兼容性矩阵。** 小程序要覆盖哪些微信版本、哪些机型、哪些系统版本？Web 要覆盖哪些浏览器（Chrome/Edge/Safari）？
5. **无安全测试。** 文档提"性能/安全测试"（01 文档 W10），但安全测什么？至少：越权、SQL 注入（MyBatis `${}` 拼接要全查）、文件上传类型校验、JWT 过期与篡改。
6. **验收标准不可测。** 7 项 KPI 里 4 项不可测。这不是 QA 能修的，是 PM 必须在 W1 定义的。

## D.5 替换建议

**R-D1　用 30 条冒烟用例替代"全量回归"。**
42 个接口不可能每次全回归。选 30 条覆盖核心链路（登录 → 搜房 → 约看 → 申请 → 签约 → 报修 → 账单 → 评价），Newman 每天跑，5 分钟出结果。这是"每天能跑"和"跑一次要两天"的区别。

**R-D2　迁移验收用"三方对账"，不用"人点一遍"。**
老库 SQL 汇总 / 新库 SQL 汇总 / 接口返回值，三者必须一致。脚本化，一条命令出报告。金额、行数、状态分布三个维度。

**R-D3　AI 只测四条硬线。**
① schema 合法 ② 超时降级不 500 ③ 空结果有兜底文案 ④ 首字节 <1s。其余交给产品做人工盲评（5 人，1-5 分）。**不要在自动化里测"聪明"。**

**R-D4　压测目标改相对值。**
不比"200 QPS"，比"优化后 P95 相对基线下降 ≥30%"。硬件写进报告首页。这样 W10 的压测才有意义，也不会因为机器差而全盘判负。

# 角色 E · 运维 / SRE 工程师

> 立场：这套系统在物理上部署不出来。不是"难"，是"矛盾"——三个约束互相打架，方案假装它们不存在。

## E.1 总体判断

**信心分 1.5 / 10。** 五个角色里最低。

前端可以降级、产品可以砍功能、后端可以退版本，**但部署不住就是部署不住**。

### 致命一：拓扑在物理上不成立

三条硬约束：

1. **小程序必须访问已备案的 HTTPS 域名**，且域名要在小程序后台白名单里，不能是 IP、不能带非常规端口、不能用免费穿透域名（ngrok/frp 公用域名不被接受）。
2. **Ollama 跑在"i5-13500K 本地"**——这是桌面 CPU，意味着机器在宿舍或实验室，没有公网 IP、没有固定带宽、晚上会断电。
3. **团队无公司主体、无备案域名**（00 文档自述）。

三条拼起来：**小程序永远连不上你的 AI。** 这不是"性能问题"，是"信号到不了"。

三条出路，W1 必须选一条：

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **(a) 全云** | 一台 8C32G 云服务器跑 MySQL + Redis + API + Ollama（3B 模型） | 约 ¥600–900/月 | 3B 效果差一档；备案仍需 1–3 周 |
| **(b) 应用上云 + AI 不上云** | 云 4C8G 跑业务，AI 降级为"规则推荐 + 模板文案"，彻底不部署 LLM | 约 ¥100–200/月 | AI 变成"规则"，需要跟老板重新对齐话术 |
| **(c) 本地 + 演示模式** | 全部本地，小程序只发体验版（关闭域名校验），交付"演示版" | 0 | 不能给真实用户用 |

**我的建议是 (b) + 备用 (c)。** AI 用规则 + 模板，把"7B 模型"作为"未来规划"写进答辩材料，这在学生项目里是完全可接受的诚实。硬上 (a) 的后果是：花 800 块一个月，跑 3B 模型，首字 5 秒，还随时可能因为宿舍断电挂掉。

### 致命二：单机资源测算缺失，16GB 会打满

如果坚持 (a)，算一笔账：

| 组件 | 常驻内存 |
|---|---|
| Ollama + qwen2.5:7b-q4 | 6–8 GB（KV cache 随上下文增长） |
| MySQL 8.0 | 1.0–1.5 GB（innodb_buffer_pool 默认 128M，实际会涨） |
| Redis 7 | 0.3–0.5 GB |
| Spring Boot (JVM 17) | 0.8–1.2 GB（堆 + 元空间 + 直接内存） |
| Nginx + OS + 监控 | 0.8 GB |
| **合计** | **9–12 GB 峰值** |

16GB 机器在 AI 推理时会触发 swap，**一旦 swap，推理从 6 tok/s 掉到 1 tok/s，AI 体验直接崩。** 而且 MySQL 会因为内存压力频繁刷盘，接口 P95 从 200ms 涨到 2s。

结论：要么 32GB，要么 AI 独立一台机器，要么模型降到 3B + 限制上下文（`num_ctx=2048`）。**方案里这句话都没有。**

### 致命三：可观测性为零，"运维手册"要写告警却没有告警源

现状：Logback 文件轮转 + traceId。就这些。

缺失：
- **Metrics**：没有 CPU / 内存 / JVM / 连接池 / 慢 SQL 的采集。
- **告警**：没有任何告警规则与通道。运维手册要写"告警"，写什么？
- **日志聚合**：5 个人 5 套环境，出问题只能 `ssh` 上去 `tail -f`，且日志分散在 4 个容器里。
- **链路追踪**：设计了 traceId（加分），但没有采集端，前端拿不到 traceId（响应头没回传），用户报障时无法定位。
- **健康检查**：`/actuator/health` 有，但没有探针、没有自动重启。

最小可行方案（1 人日）：compose 里加 Prometheus + Grafana + Loki，Spring Boot 暴露 `/actuator/prometheus`，3 条告警规则（服务 down / 错误率 >5% / P95 >2s）。**这是 1 天的工作，能省掉上线后 3 天的瞎猜。**

### 致命四：容器化排到 W12，等于前 11 周 5 个人 5 套环境

01 文档 W4 写"CI 跑通"，W12 才写 Dockerfile。

后果：
- 前 11 周，5 个人各自装 JDK、MySQL、Redis、Ollama，版本不一致。
- 联调时"我这能跑你那不能跑"，会被误判为 Bug，浪费的是全队的时间。
- W12 才第一次打包镜像 = 第一次发现端口、路径、时区、字符集、文件权限问题，且没有时间修。

**`docker-compose.yml` 应该是 W1 的交付物**，不是 W12 的。它解决的不是"部署"，是"环境一致性"。

## E.3 硬伤

### P0（不改会失败）

**P0-E1　W1 定部署拓扑，三选一并写进文档。** 见 E.1 表格。推荐 (b)：应用上云（4C8G，约 ¥150/月）+ AI 降级为规则推荐。把"7B 本地部署"作为二期规划。**这条不定，W8 的 AI 开发和 W12 的部署都是空转。**

**P0-E2　资源与成本表。** 一张表，四行：机器规格、月成本、能支撑的并发、瓶颈在哪。老板问"多少钱"必须 30 秒内答出来。

**P0-E3　`docker-compose.yml` 提前到 W1。**
内容：mysql8 + redis + api + nginx + （可选）ollama + prometheus + grafana。一个人一天能写完。收益：5 个人环境一致、新人入职 10 分钟起环境、W12 部署不慌。

**P0-E4　可观测性最小集，W4 前落地。**
Actuator + Micrometer + Prometheus + Grafana + Loki。3 条告警规则。traceId 通过响应头回传。**没有这些，上线后所有问题都只能靠猜。**

**P0-E5　备份 + 回滚，W2 定策略、W11 演练。**
- 备份：`mysqldump` 每日全量 + binlog，保留 7 天，存异地（对象存储或另一台机器）。
- 回滚：上一版镜像 tag 保留 3 个 + 数据库迁移的回滚脚本 + **一次真实演练**（W11，限时 30 分钟恢复）。
- 单机部署的回滚窗口 = 停机窗口，这个必须提前告知老板。

### P1（不改会延期 / 体验差）

- **P1-E1　无灰度能力。** 单机 + 无负载均衡 = 无法切流量。"灰度 10% 租客"要么改成"灰度 10% 内部账号"，要么加一台 Nginx 做权重（成本翻倍，不值得）。建议直接改口径：**"体验版分发 + 内部账号验证"**，别用"灰度"这个词。
- **P1-E2　无 CDN / 无对象存储。** 房源图片走服务器本地磁盘：流量费 + 磁盘满 + 备份困难。最小方案：图床用对象存储（¥5/月起），或至少 Nginx 开 `gzip` + `expires 7d` + 生成缩略图。
- **P1-E3　时区与字符集。** MySQL 8 默认 `utf8mb4_0900_ai_ci`，JDBC 要显式 `serverTimezone=Asia/Shanghai`，容器要挂 `TZ=Asia/Shanghai`。这三处不写，日期会差 8 小时（正好是 D 角色说的"人点一遍发现不了"的坑）。
- **P1-E4　Ollama 与应用的资源竞争。** 同机时，AI 推理会抢 CPU，导致业务接口 P95 抖动。必须：AI 请求限流（信号量 2）+ 模型 `num_thread` 限制 + 业务接口独立线程池。
- **P1-E5　无 CI/CD。** 01 文档 W4 提"CI 跑通"，但没有流水线设计。最小：GitHub Actions（或 Gitee Go）+ 三条 job（build / test / docker push），半天搭完。没有 CI，W11 的"每天跑冒烟"落不了地。

### P2（建议优化）

- 日志改 JSON 结构化（`logstash-logback-encoder`），Loki 才能按字段查。
- 加 `/actuator/info` 暴露 git commit + 构建时间，回滚时能确认版本。
- Nginx 加 `client_max_body_size 10m`（报修多图上传会撞默认 1m 限制，这是个必踩的坑）。
- 数据库连接池 HikariCP 的 `maximum-pool-size` 要按"CPU 核数 × 2 + 磁盘数"设，默认 10 在单机上偏大。

## E.4 漏掉的关键事项

1. **可用性目标。** 没有 SLA 定义。是"7×24"还是"演示时能跑"？这决定了要不要做主备、要不要买高可用。
2. **故障预案。** 断电、磁盘满、OOM、Ollama 卡死、MySQL 连接耗尽——五个场景，一个预案都没有。
3. **证书与域名生命周期。** HTTPS 证书 90 天到期（Let's Encrypt），谁续？域名年费谁付？到期忘续 = 全站挂。
4. **带宽。** 小程序加载图片 + Web 大屏图表，2M 带宽够不够？没算过。
5. **发布流程。** 谁有生产权限？发布要不要审批？现在是 5 个人都能改线上？
6. **数据合规。** 用户手机号、openid、身份证（如果要实名）的存储与脱敏，一条没提。
7. **Ollama 模型的持久化。** 模型文件 4.7GB，容器重建就没了（除非挂 volume）。这个坑第一次部署必踩。

## E.5 替换建议

**R-E1　部署形态改成"应用上云 + AI 可选"。**
- 基线（必做）：4C8G 云服务器，Docker Compose 全栈（mysql + redis + api + nginx + prometheus + grafana），月成本 ¥150–250。
- AI 增强（可选）：如果能搞到 32GB 内存机器，加一个 ollama 服务（3B 模型，`num_ctx=2048`，限流 2 并发）；否则走规则推荐 + 模板文案。
- 这条把"物理不成立"变成"物理成立但不完美"，是可交付的。

**R-E2　可观测性用"3 个指标 + 1 个面板"起步。**
不要一上来搞全套。三个指标：错误率、P95、JVM 堆使用率。一个面板：Grafana 单页。3 条告警：服务 down / 错误率 >5% / 堆 >85%。1 人日，覆盖 90% 的线上问题。

**R-E3　回滚用"镜像 tag + 数据库向前兼容"，不用"数据库回滚"。**
数据库回滚（down migration）在生产上极危险且经常不可行。正确做法：迁移只做**向前兼容**的变更（加字段不删字段、加表不改表），回滚只回镜像。这样回滚 = `docker compose up` 上一个 tag，30 秒完成。**这条能让 W11 的回滚演练从"不可能"变成"演示级"。**

**R-E4　灰度改"内部账号 + 体验版"。**
5 个人 + 20 个同学当灰度用户，用体验版二维码分发。真实、可执行、成本 0。别在文档里写"10% 租客"——没有 10% 的租客。

| 2. 双向评分 | A / B | **结构完整，不可运行** | 官方分无供给、冷启动无解、租约无结束事件、租客分无申诉 |

| 4. 报修 + 缴费 | B | **合理降级，确认太晚** | 降级是对的，但老板签字应在 W1 而非 W7 |
| 5. 性能优化（老旧配置升级） | A / E | **被彻底替换** | 老板说换机器，方案做了框架升级；无规格、无成本、无容量模型 |

## 五个角色的一致意见（不需要再讨论的）

1. **W1 必须解决三件事**：部署拓扑决策、依赖 spike、验收口径书面化。这三件不做，后面 11 周都在还债。
2. **范围必须砍 30%**：RAG 向量库、bill 三表、巡检模块、Web 全量重写、暗色模式、高德热力图。
3. **必须从"串行联调"改成"契约先行 + mock"**：这是唯一能把 12 周拉回来的动作，五个角色无一反对。
4. **必须造数据**：17 条种子（F10）撑不起评分/推荐/账单三个模块的演示。
5. **必须承认这是"可演示交付"，不是"上线运营"**：除非备案与类目在 W8 前通过。

## 一句话总结

> 这份方案的文档质量远高于它的工程可行性。三个物理约束（备案域名、桌面 CPU 上的 Ollama、没有设计师）和一个人力约束（BE 单人扛迁移）没被承认。前三个不解决，W12 交付的是一段视频，不是一个系统。
>
> 但它是可救的：退 Boot 版本、砍 30% 范围、契约先行并行开发、AI 降级为规则 + 文案、UI 只做 4 页 —— 这五刀下去，12 周能交付一个"能演示、能讲清楚、没有明显硬伤"的系统。这比"什么都做、什么都做不好"强得多。
